The [README](../README.md) covers usage and deployment. This document covers implementation, commit boundaries, and recovery. ## Control principles

- Administrator APIs check identity and CSRF on the server. Hiding a button is not authorization. A successful administrator login replaces the previous session; a failed login leaves it intact.
- Storage changes may cancel unfinished uploads without requiring users to stop them first. Committed files stay in place. Cancellation cleanup touches only the task's temporary data.
- Keep user actions simple without removing the identifiers needed for atomic commits, temporary-data ownership, capacity accounting, and recovery.
- Direct S3 uploads exchange file data between the browser and object storage. Relay uploads are for clients that cannot reach storage directly, whether the storage is public or private.

`auth.rs` handles HTTP login and request authorization. `auth/login.rs` defines credential snapshots and the checks before issuing a session. `auth/session.rs` owns bounded sessions and scoped access tokens; `auth/password.rs` handles password computation and two-factor proofs. Browser and WebDAV login share password-length validation. Administrator login replaces the old administrator session; user and folder tokens are revoked by their own scope. Password tasks retain their concurrency permits until computation finishes, even if the HTTP waiter is cancelled.

Login captures a named credential snapshot for the requested entry point. Ordinary user login does not copy administrator two-factor secrets. After password verification, the shared `auth_transitions` lock protects a second check of account identity, password, and any required second-factor proof. Only then is the proof consumed and a session issued. A revoked snapshot cannot recreate a session. Failure paths share durable failure records and responses rather than using an empty user ID as a fallback. Site-password and login-policy checks use one configuration read. Account name, enabled state, and site-password requirements in `me` also use one configuration snapshot; the whole response is not an atomic observation of both session and configuration state.

Administrator and user sessions expire 24 hours after login. Site and folder access tokens expire after 7 days. Access does not extend either lifetime. Persistent cookies can survive a browser close or computer restart; they store random tokens, not plaintext passwords. Server restarts invalidate the in-memory sessions. There is no separate “remember me” option.

Site access and administrator login are independent. Refreshing `/admin` or `/admin/...` opens the administrator entry point without first asking for the site password. Administrator APIs still require administrator authorization. The site access page is `/`; existing valid account or site-access tokens can pass under the normal rules. Rebuilding does not revoke credentials in a running service. Restarting the process clears its in-memory sessions.

File-browser and administrator clients share `/api/logout`, response validation, and a bounded wait. Logout is confirmed only when HTTP succeeds and the body explicitly contains `success: true`. It has a 10-second wait; other APIs retain their 330-second budget. Before confirmation, the file browser does not dispose its listing, mark itself signed out, or redirect. Repeated clicks do not send concurrent logout requests. Network failures and error responses are not success. Users can explicitly sign out again after reconnecting; business writes are not retried automatically. A late result cannot redirect a newly mounted page, and failure to store a local preference cannot block a confirmed logout.

The server captures the session, site-access, and folder cookies from the request, then obtains write locks for all three credential stores. Nothing is removed until all locks are held. Deletion has no asynchronous waits, after which the response expires the cookies and confirms success. Cancellation while waiting cannot revoke only part of the set. Logout is idempotent and revokes only the received tokens, not sessions on other devices, account records, or storage/WebDAV keys. It cannot confirm delivery of a request during a network outage and is not a global logout or persistent-session mechanism.

`security.rs` selects the client IP at the shared request boundary. Login logs, failure limits, and bans use that address. Trusted proxy IPs are saved with the domain binding and take effect immediately, without environment variables or a restart. Only an exact allowlisted TCP peer can supply a single valid `X-Real-IP`. The list accepts at most 16 IPv4/IPv6 addresses; saving normalizes IPv4-mapped IPv6, sorts, and deduplicates them. Clearing the list disables header trust; removing the domain also clears the list. Untrusted headers are ignored. A trusted peer without the header keeps its connection address; duplicate or invalid values return 400. The proxy must overwrite rather than append the header. Ycloud does not parse forwarding chains, infer trust from private addresses or HTTPS domains, or use `X-Forwarded-For`/`Forwarded`. Configuration version 16 keeps the bound domain but initializes obsolete proxy fields to an empty list during migration; explicitly saved current lists survive restart. Historical logs stay unchanged. Administrators must review bans that were recorded against a proxy address; security records are not cleared automatically.

Ordinary navigation within the admin console uses the History API, keeping the shell and loaded configuration mounted. Each navigation still reloads configuration and checks authorization; 401/403 opens login. Browser history, direct links, and refresh work. Modified or non-left clicks keep ordinary link behavior. Leaving the console follows the full-page lifecycle. The storage page polls every five minutes only while active and visible; unmount removes timers and listeners. Page-specific reads and drafts leave with their page. Initial loads, API requests, and navigation between entry points still require network requests. There is no SSR, general router framework, or offline configuration cache.

Embedded HTML, JavaScript, CSS, and the favicon use content-based SHA-256 ETags, computed once per resource per process. Matching GET/HEAD conditions return an empty 304; changed content gets a new response. Fixed resource URLs use `Cache-Control: no-cache`, requiring revalidation rather than an immutable long-lived cache. HTML does not cache account or configuration state. This does not change API, file-content, or authentication policy. NPM or a CDN may alter conditional requests; cross-region load times still need deployment testing.

The login entry is loaded synchronously. The file browser, standalone preview, admin shell, and individual settings pages load as Vue async components. `shared/lazyPage.ts` provides only code-loading and error handling: show loading immediately, then an error if code has not loaded within 30 seconds. This wait does not cancel transfers or API calls. Loaded modules are reused within the current document; unmounted page instances and sensitive drafts are not retained. Errors offer manual refresh with a reminder about unfinished operations, not automatic refresh, write retries, or unlimited retry loops. Later admin navigation still rechecks authorization and configuration. A smaller entry bundle is not proof of acceptable load times on a weak connection to Hong Kong.

Vite keeps a fixed `app.js` entry and one complete `app.css`; lazy JavaScript chunks have content-hashed names so a running page does not mix chunk versions. `build/embeddedAssets.ts` generates `static/app/embedded-assets.rs` from the actual build output. It accepts the current flat JS/CSS names and rejects duplicates, unsupported types, or a missing entry. New asset types, such as images or fonts, need explicit manifest and MIME support. Rust's `app/frontend_assets.rs` embeds this ordered manifest and serves resources by allowlist, retaining per-resource ETags and `no-cache`. It neither reads arbitrary requested disk paths nor substitutes HTML for a missing chunk. A missing manifest file fails Rust compilation; new chunks need no handwritten backend route. CI checks untracked build output as well as changes to tracked files.

Releases must include all of `static/app/`, including the generated manifest. The Dockerfile already copies the directory as a whole; no runtime asset path or environment variable is needed. An old open page may get 404 when it requests an old hashed chunk after redeployment. Refresh manually after checking for unfinished operations. The service does not retain every historical chunk or discard page tasks through automatic refresh. Historical “over 500 kB” build notes describe those builds, not the current bundle.

## Configuration publication and storage changes

The configuration model defines initial settings. First start supplies independently generated administrator and site-password hashes, then narrows transfer limits to the deployment limits. `config/credentials.rs` converts S3 and TOTP credentials, reading the configuration key once per conversion. Read-only decoding of a plaintext candidate does not create a key. `persistence.rs` coordinates loading and saving; `commit.rs` owns atomic file publication and backup paths. Publication does not depend back on loading. Ciphertext remains bound to storage identity, provider, and field. Legacy migration and full candidate validation precede publication.

`state.rs` separates remote preparation from configuration publication. Storage edits use non-queued admission: an edit already in progress produces a conflict. Connection preparation has a 60-second cooperative cancellation budget, not a blanket timeout that discards writes to final objects. A connection change first interrupts and drains the old instance, then prepares the candidate. Failed preparation or publication keeps the original configuration. Old admission resumes only after the old executor exits; cancelled transfers do not resume. Preparing a new storage instance does not disturb others.

`state/storage_update.rs` owns the shared local/S3 edit lifecycle. A small pure decision distinguishes no change, re-enable, policy interruption, and connection replacement. Ticket invalidation is separate so re-enabling while restricting permissions cannot miss it. Both edit paths acquire the old admission gate, prepare a candidate, retain old cleanup responsibility and save, invalidate tickets, retire, and publish in the same order. The edit guard lasts through publication. Connection identity excludes live capacity policy and the S3 relay switch; all other S3 fields participate. Without a cached instance, reuse cannot be claimed. Each entry point still handles paths, mount selection, and credential backfill. Existing implementations handle initialization and local/S3 recovery. Initialization or save errors do not retire the original instance, publish a new quota, or revive cancelled requests.

Enabled storage initializes sequentially at startup, sharing one 60-second deadline for admission and cooperative cancellation. It is not 60 seconds per storage. Once the deadline expires, no further instance starts; remaining instances are marked unavailable. Failed initialization does not loop indefinitely, and administrators can retry. Issued S3 writes to final objects wait for the SDK call to return; local publication and recovery are not dropped from outside. SDK requests and filesystem synchronization can exceed the budget, which is not a hard OS I/O deadline. Initialization tests the connection and recovers authenticated Ycloud transactions; it does not empty a bucket or remove objects without ownership evidence. Ready instances use their normal clients, not clients that expire with the startup deadline.

The runtime registry distinguishes ready, disabled, and unavailable storage. Only ready instances outside interruption settlement accept new file requests. Disabled instances retain their old backends for status and necessary maintenance; unavailable entries have no cacheable backend. The admin console uses the existing `pending` state to show processing, while the connection indicator retains the last cached result. A saved configuration does not mean the instance is serving requests. Disabled storage is shown as disabled, not as an initialized connection.

Disabling, removing, restricting guest access/downloads, or changing relay mode closes admission and cancels old transfers before settings are published. It does not wait for an entire file change or garbage cleanup. An undrained `StorageEditGuard` passes its gate to the instance's single background settlement executor; repeated disable requests do not start extra settlers. Re-enable checks old executors, recovery/capacity gates, and pending journals. Before a safe boundary, it rejects the request and keeps the disabled configuration rather than enabling automatically. Changing a connection or mount path still drains the old instance to protect namespace and capacity-ledger identity. It waits at most 5 seconds, then returns a conflict without changing configuration. Selecting disable at the same time does not bypass this rule.

Administrator interruption also pauses S3 admission and cancellable reads, including directory/capacity scans, recovery listings, journal reads, and HEAD verification. Only deletes inside the internal temporary namespace and Multipart Abort can be interrupted; durable records remain for later processing. `s3_backend/maintenance.rs` captures a cancellation generation, optional stop flag, and deadline at the start of a long operation. Nested work inherits that generation and can only shorten the deadline. PUT/COPY/DELETE on final objects and issued stage-journal writes are not dropped. Expiry stops work at the next read or admission check. Resuming backend requests does not revive old work. The settlement executor keeps the old gate until file owners and S3/capacity recovery drain. Retired backends remain closed to users but can clean up through their original connections.

Existing serial workers handle old-connection cleanup and unknown uploads. Each instance gets a 30-second cooperative cancellation budget per pass, so a slow instance does not consume every other instance's next budget. Shutdown cancels cancellable phases, then waits for issued writes to final objects; it does not discard the recovery future. Directory completion waits separately for the stage journal before allowing up to 500 ms for temporary cleanup. Once commit completion is proven, a journal or cleanup error does not turn it into an uncommitted result. Full local recovery retains its entry and cleanup budgets but has no fixed wall-clock guarantee.

The global configuration-publication lock has a 5-second acquisition wait. Storage saves merge only storage fields into the latest configuration, preserving intervening account or transfer-setting edits. Memory is published after disk success. Required commits continue after the HTTP client disconnects. At most four administrator writes execute concurrently; excess requests are rejected, not queued without a bound. Atomic disk publication still depends on the OS, and the lock wait does not forcibly interrupt a disk commit already underway.

Name, permission, and capacity edits reuse the existing instance. Name/capacity changes and relaxed guest policies do not interrupt transfers; stricter guest policies do. Connection changes, disable, removal, and upload-mode changes also cancel old transfers. New-connection initialization and recovery run outside the global configuration lock. Login-log compaction runs in the background only when retention policy changes, not on every configuration save.

Upload name selection captures the process-local storage-change generation. If storage is changed or disabled before ticket creation, the old plan is rejected and must be prepared again. Generation checks and old-ticket invalidation share the batch lock; administrators do not wait for a directory scan.

Durable upload-ticket changes serialize per ticket, not under the global batch-table lock during disk waits. A new ticket reserves its slot and paths in the table, then a separate creator publishes the manifest. The ticket is returned only after publication and a matching storage generation. A slow write does not block other batches from starting, finishing, or reading status. Settling tickets are not expired or evicted under pressure. Within a ticket, durable state still precedes memory. Invalidating unstarted items does not wait for ticket disk writes; after a start write returns, cancellation is checked again. Cancelled uploads cannot be revived. Index format and account/global budgets are unchanged.

Transfer and login-protection edits send only changed fields. User, storage, WebDAV, and folder-lock edits carry opaque revision tokens, checked under the corresponding update lock. A changed record rejects the stale form. Tokens are HMACs under a process-local random key, expose no secret values, and become invalid after restart. They are API fields, not a disk configuration-version change. Older clients without tokens remain compatible but lack stale-form protection.

Storage-form defaults, edit backfill, provider-address defaults, capacity validation, and S3 request conversion live in `apps/admin/useStorageForm.ts`. `StorageView.vue` keeps connection tests, request revisions, enable-after-create, and save/delete coordination. Editing clears credential inputs; blank inputs retain existing keys. Connection fields are trimmed, keys are not. Turning off guest access also turns off guest downloads. If a form changes during a connection test, a late result cannot replace current feedback. Request and server publication rules are unchanged.

`apps/admin/userAccountForm.ts` owns permission drafts, related permission changes, and create/diff request conversion; `UsersView.vue` keeps traffic reads, UI, and requests. Diffs compare named fields, not JSON insertion order. Storage-array order is retained. Requests copy permissions and quotas rather than sharing a still-editable draft. Blank passwords are omitted, replacement passwords are sent unchanged, and usernames alone are trimmed. Revision tokens and default-quota writes remain intact. User and shared quota edits reuse `trafficQuota.ts` for defaults, comparison, and nonnegative safe-integer byte validation; display formatting stays specific to each page.

WebDAV and folder-lock path formatting and request diffs live in `apps/admin/storageAccessForm.ts`. Edit buttons and save requests use the same diff, while pages add the original revision token and handle validation, requests, and feedback. Formatting normalizes separators only: it does not parse URLs or dot segments, trim filename whitespace, or replace backend path/scope checks. A blank password in a WebDAV update still explicitly clears it; empty credentials on creation are omitted. Folder locks still reject root paths and password removal in their page. Administrator, WebDAV, and folder-lock pages share masking and deferred selection through `shared/passwordInput.ts`, not their password requirements or submission semantics.

`apps/admin/useTransferLimitsForm.ts` owns the seven limit inputs, exact byte baselines, deployment-limit validation, and request diffs. `LimitsView.vue` owns the editor, requests, busy state, and feedback. Displayed GiB/MiB precision is not the stored configuration. Untouched size and rate fields keep the original byte values rather than being rounded and resubmitted with unrelated edits. Backfill, reset, and post-save display use one mapping, with separate drafts and baselines. The module performs no network or account/authentication reads. Server limits, older-response defaults, and response-confirmation rules are unchanged.

`apps/admin/loginProtectionForm.ts` handles backfill, four-field diffs, and validation without Vue or network dependencies. `ProtectionView.vue` manages reactive drafts, UI, and save feedback. Changed-state checks and submission share field comparison; controls and validation share constants. The backend accepts ban duration in seconds. An untouched duration keeps its exact seconds rather than being forced to whole minutes or blocking an edit to the failure count. Explicit duration edits still require 5–1440 whole minutes. This module does not handle log retention or change authorization or login limits.

`apps/admin/useSecurityLogs.ts` manages filters, applied search, pagination, the latest query, and periodic refresh. `SecurityView.vue` keeps display, clear/ban confirmation, and retention-policy writes. Reads use the admin client's cancellation and deadline; replacement queries and unmount cancel old reads and reject late results by revision. A completed write cannot start a refresh after disposal. Cancelling a query does not cancel an accepted administrator write. Repeated policy saves are ignored. Confirmed saves and bans are reported before an independent list refresh; read failure is shown separately and neither delays nor reverses the write result. No write is resent automatically. Page sizes, refresh intervals, and pauses for dialogs or non-first pages are unchanged.

`apps/admin/useAdministratorTotp.ts` owns two-factor preparation, enable/disable, copy feedback, and sensitive-draft lifetime. `AccountView.vue` keeps account credentials, site-password-removal confirmation, display, and re-login timing; domain binding stays separate. The three two-factor requests share one busy state but retain their APIs and errors. Passwords are sent unchanged; verification/recovery codes are trimmed. Enable clears the password, verification code, and setup secret, keeping one-time recovery codes until the user closes the view. Confirmed disable immediately asks the user to sign in again. Close/unmount clears draft references, and late results do not refill a disposed page. Accepted writes are not cancelled or repeated automatically. Clearing references is not a guarantee of physical JavaScript memory erasure.

`apps/admin/adminAccountForm.ts` handles account backfill, diffs, and minimum password length. The page retains requests, busy state, site-password-removal confirmation, and feedback. Buttons and submission use the same diffs; re-login is decided from the username/administrator-password fields actually sent. Usernames are trimmed; passwords are unchanged. An unchanged mask is omitted, and an empty site-password string explicitly removes it. With no existing site password, a mask-like input is validated as a new password and cannot bypass minimum length. The rules read only username and site-password presence, not network state, two-factor settings, or domain settings. The backend remains responsible for final authorization and validation.

`apps/admin/useDomainBinding.ts` owns domain reads, save/removal, drafts, and lifecycle. `DomainBindingSetting.vue` handles display and feedback. Confirming an HTTPS address saves it; clearing it and confirming calls the existing DELETE endpoint. There is no separate remove button, extra confirmation page, or open-domain link. Operations share a busy state without duplicate reads or queued writes. Confirmed save/removal responses use the same application rules but retain their own APIs and messages. Known state and drafts are separate; display/backfill use the normalized server response, not the sent draft as proof of success. Read failure keeps known state and reports separately, while explicit saves remain available. Failed save/removal retains the draft and does not resend an unknown operation. Cancel clears editing; unmount cancels reads and ignores late responses, not accepted writes. Backend domain validation and immediate activation are unchanged.

The dashboard defaults to the last 7 days. Today, 7-day, and 30-day presets query with `days`; the backend calculates ledger dates from the traffic cycle's `offset_minutes` and current time. The response's `today` also limits custom end dates. Browser-local dates no longer make preset requests differ from UTC or Beijing time near midnight. Custom ranges remain within retention and at most 31 days. `days` cannot be combined with explicit dates. Older requests without date parameters still return the current month. A new deployment with no transfers returns zero usage and a complete date series rather than hiding the chart. Ledger dates, history, and reset cycles are not migrated.

`apps/admin/useAdminSession.ts` coordinates admin login, configuration reads, storage refresh, and session-expiry timing. `AdminView.vue` keeps navigation, page composition, and feedback. Navigation uses shared path normalization and existing items. Reads use cancellation and deadlines; replacement/unmount cancels old requests and rejects late results. Login errors and read errors stay separate. Storage refresh remains every five minutes, skipped while hidden, requiring login, logging in, or already reading. Confirmed operations report success before background refresh without unmounting the current settings page; refresh failure is separate and never repeats the write. Logout after an ordinary user enters the console also uses the bounded client. Unmount stops timers and clears local password/code references. Sent login/logout requests are not cancelled and cannot start reads after disposal. Server authorization, login proofs, and revocation rules are unchanged.

## Results and recovery

Browser uploads save duplicate names as `filename (number).extension`, continuing from the highest existing suffix. Tasks show the saved name. WebDAV retains client write semantics. Queue deduplication uses the original destination, not a server-generated suffix. A storage change during name selection requires new preparation; numbering from the old directory is not carried to a new connection.

`s3_backend/copy.rs` handles single-file copy preparation, execution, verification, and failure rollback through the backend's existing COPY/HEAD/DELETE primitives. After COPY is accepted, failed verification reads, including administrator pause, a missing destination, or an identity mismatch mean the commit is unknown, not an ordinary retryable failure. Rollback deletes only a destination matching the COPY response ETag, using a conditional delete and confirming absence before reporting not committed/cleanup complete. A delete substep's failure cannot prove the entire copy was uncommitted. An object whose identity changed is not deleted. Unknown results still trigger capacity reconciliation, but a capacity scan is not durable proof of this copy. This entry point adds no cross-restart receipt or automatic result-verification task.

`storage_backend/lifecycle.rs` owns operation admission and administrator interruption: lifecycle leases, cancellation markers, independent write owners, and edit guards. Each instance retains its 32-write budget. Connection/mount changes wait at most 5 seconds to drain; policy publication does not wait for an entire file operation. Cancellation or timeout does not reopen admission before old owners exit. Old cancellation markers stay cancelled after admission reopens. A failed write task reports unknown commit/cleanup rather than a definite failure or automatic retransmission. `StorageEditGuard` keeps its public path; transaction proofs and S3 gates are unchanged. All three storage constructors use `ActiveStorage::new` for independent runtime state without sharing gates/capacity or implicitly scanning, recovering, or starting workers.

S3 `copy_path` runs through its already-acquired write owner, without a second nested executor, cloned request paths, or extra snapshot-invalidation guard. File and directory branches estimate and reserve capacity, acquire the capacity-change gate, and recheck source size through the remote copy entry. `S3CapacityAccounting` deduplicates reconciliation on error or abnormal exit, replacing duplicate explicit checks and nested JoinError handling. Task failure is reported as unknown by the write owner. A verified copy commits its reservation and ledger once. Snapshot invalidation and admission/execution budgets last until work really finishes; disconnecting the HTTP waiter does not cancel an accepted copy. Local copy keeps its distinct direct-call boundary; uploads retain their separate transfer/commit ownership. Directory commit, authenticated remote records, conditional ETags, and recovery rules are unchanged.

`storage_backend/maintenance.rs` coordinates background storage work; the unified interface only starts or triggers it. Local/S3 implementations still own scanning, ledger publication, and transaction recovery. Retry delays range from 1 to 60 seconds; the recovery quiet period is 1 second. The local worker holds no strong instance reference while waiting/retrying. It obtains the lifecycle read gate before reconciliation and stops scanning retired instances. The existing tracker deduplicates claims. The S3 worker keeps its single-start, shutdown notification, exclusive recovery, and commit rules. It does not forcibly time out a transaction, guarantee a whole-pass duration, or guarantee immediate interruption of S3 capacity retry sleep.

`s3_backend/recovery_runtime.rs` keeps pending work, recovering status, consecutive failures, failure details, and retry time in one locked `RecoveryState`. Duplicate registration keeps the original timestamp. A successful pass clears current recovery/retry state, not historical failure details or all pending work. A journal settles only after deletion or absence is confirmed. Journal absence allows that recovery item to exit; it does not prove file success or failure. Failure counts saturate. Worker claims, stop flags, and two Notify objects remain separate lifecycle/wakeup mechanisms. The state lock never spans network I/O; successful settlement still requires the exclusive recovery gate. Orphan counts are supplied independently, so the entire backend view is not one atomic snapshot.

After obtaining exclusive recovery admission, runtime S3 recovery takes a pending-work snapshot, validates the exact namespace, journal category, and transaction ID, and chooses one record in the established order. It reads the record directly and reuses startup recovery's authentication/execution algorithm rather than scanning six categories for each pending key. Upload transactions precede internal upload intents. Intent cleanup must also confirm that the same-ID upload transaction is absent; an associated transaction or read/authentication failure retains the intent and resources. Each record releases recovery/mutation gates and yields. Only after all registered journals settle does recovery run read-only orphan listings for uploads/backups. If recovery made capacity uncertain, final settlement schedules reconciliation, including when foreground work removed the final journal between passes. A stop while waiting for the gate clears recovering state after acquisition without dropping responsibility/history or issuing remote work.

One record per pass is not a request-count or elapsed-time bound. The snapshot still walks all registered keys, a directory transaction can involve 1000 objects, and final orphan listings need safe pagination. PUT/COPY/DELETE on final objects calls are not forcibly cancelled. An unresolved high-priority record keeps the existing failure backoff and may block later records; scheduling does not bypass dependencies. Startup and post-interruption recovery still perform full namespace checks. No durable queue, configuration, or record format is added.

`storage_transaction/recovery.rs` first settles in-memory pending-publication records, then validates bounded transaction journals, upload/copy staging listings, and one page of trash before recovering replacements and cleaning staging. During the read it derives an in-memory anchor-claim index by transaction ID, avoiding a full journal scan for every anchor. This is not commit proof. Undeclared journal-owned anchors reject recovery; orphan anchors without journals use the existing cleanup rules. Execution still verifies file identity and publication proof, and deletes the journal last. Under exclusive recovery, validated copy staging with no active executor is renamed into trash under its original ID and both directories are synced. Same-ID target or complete/incomplete deletion-record conflicts retain resources and reject ownership guesses. The online worker does not independently scan and take over copy staging.

Startup receipt counts and expiry cleanup share the transaction-directory listing. Linux enumeration and metadata reads are bound to the opened root, not a reopened absolute path. Receipt IDs are 32 lowercase hexadecimal characters, distinct from transaction UUIDs. Type and name checks precede staging or expiry handling. The scan allows 100,000 receipts and at most one staging file per receipt, not the 4096-transaction-journal budget. Exceeding the scan budget preserves resources and returns an error.

Each local recovery pass deletes at most 256 file/directory nodes from trash; it does not loop until the whole tree is gone. The online cleanup worker handles remaining trash and deletion debt. Listings use the existing 4096-entry page budget so copy handoff cannot make trash block restart. An unmatched record is removed only after its corresponding trash is individually confirmed absent and the directory is synced; absence from a page is not proof of deletion. Partial and unprocessed trees keep their records. The node budget does not cover replacement recovery, listing reads, single-file staging cleanup, copy renames, or directory synchronization, and is not a whole-pass time guarantee.

Configuration and login-protection state share the private atomic-file publication boundary. Pre-publication failure leaves memory unchanged. Backup refresh or directory-sync failure after publication logs a warning, not a false claim that the save failed. Login limits persist their candidate before updating memory; failed event-log append does not reverse an effective restriction.

`storage/cleanup.rs` separates cleanup settlement from scheduling. One locked `CleanupState` holds known debt entries and the public summary. Registration and confirmed batch completion update together; a scan snapshot cannot overwrite newly registered debt. Only confirmed paths reduce debt. Failed or incomplete trees remain. Missing byte records, truncated listings, or failed scans cannot be presented as complete statistics. Byte totals use saturating addition and are recomputed after completion, not subtracted from an already saturated total. Before serving, bounded disk listings initialize debt/completeness and wake the worker for leftovers; successful exclusive recovery also notifies it. Unknown-size copy staging gets no invented byte count. Locks do not span file I/O. Existing scan/delete/sync rules, 256-node batches, backoff, and final shutdown cleanup remain; I/O and mutation gates are released after each batch. Disk debt remains the durable work source.

If a verifiable settings write loses its response, the frontend reads current state without resending the write. Quotas, login protection, transfer limits, and some entity edits/deletes can be confirmed this way. Creation and hidden-password changes cannot be proven from a list alone. Unreachable or inconclusive reads leave the result unconfirmed, not successful. This uses existing requests, not a new task queue.

Uploads use existing commit/cleanup state and operation markers for automatic confirmation, without a manual verification entry point. If direct-upload parts all arrive but the final confirmation request is lost, the idle timeout triggers inspection and completion. The backend attempts recovery and updates task state every 15 seconds; that is a scheduling interval, not a completion guarantee. Committed files stay. Unfinished temporary data and known-ID multipart sessions are reclaimed; empty sessions without an ID rely on bucket lifecycle rules. Unreachable storage defers retries rather than deleting final files or other tasks' data. Unsettled tasks keep their original backend references after edits/removal and group recovery by backend instance, never by a reused storage ID alone. Unsettled responsibility outlives normal batch TTL and releases the old backend only after settlement.

`upload_recovery.rs` separates backend binding for the pass from recovery execution. Existing references take precedence; unbound namespace-marked items are checked individually, while old tickets without markers retain compatibility rules. Current namespace and backend lookup, including an unavailable result, are each computed once per storage for the pass, then refreshed next pass. It does not clone the whole credential-bearing configuration. Configuration locks end before asynchronous lookup/recovery I/O. Work remains grouped by backend identity and recovered exclusively, with at most 32 confirmations per group using positive commit evidence only. This count is not a total I/O or time budget.

The cleanup worker's `UploadRecovery` stores only the next confirmation position for each backend, not copied tasks, states, backend references, or a durable ordering hint. Unknown items are stably sorted by instance, ticket, and path. Each pass wraps from the previous position and attempts at most 32 distinct items. Every attempt advances, including conflicts and storage errors, preventing a persistent unknown/error prefix from monopolizing the window. A group blocked by an active owner does not advance. Hints for instances without bound unknown items are removed; shrinking sets normalize the position. Restart begins at the start without changing durable results. A stable set eventually gets examined, but a changing set or slow storage has no fixed settlement deadline.

Ticket persistence and runtime reservation finish in one independent executor, which holds name-selection admission through creation. Disconnect during a disk write cannot leave only a durable ticket without its runtime reservation, or accumulate unbounded preparation waiters. A client that never received the ticket must prepare again; orphan pending tickets expire under retention. Recovery confirms unknown uploads only from durable evidence tied to that operation. A missing current file or S3 marker does not prove “never committed” and cannot turn unknown into failed. Without positive or explicit negative evidence, the result stays unknown and retains recovery responsibility. Definite not-committed/cleanup-complete failures remain retryable.

`upload_batch/item.rs` defines item state and rules. The ticket owns authentication, storage/path/size binding, locks, persistence, and runtime updates; `persistence.rs` owns index I/O. Active quota, name reservation, and retention share terminal-state rules, while recovery responsibility shares running/unknown rules. Cancellation still applies only to unstarted or definite failed items, not completed or awaiting-confirmation items. Start decisions and result classification do not mutate items; durable InProgress precedes the memory update. Committed takes precedence over cleanup. Unknown commit, or not committed with incomplete cleanup, remains Unknown. On restart, Pending becomes Cancelled and InProgress becomes Unknown; known results and operation evidence stay, and transfer is not reopened automatically. `UploadStatus` and `UploadBegin` keep their public paths and serialization names. The unused boolean settlement helper is compiled only for tests.

Ticket admission derives active batches, account batches, active items, and retained items once under the lock rather than maintaining cached counters. Limits remain 32 active batches globally, 4 per account, 20,000 active items, 128 retained batches, and 40,000 retained items. Only under retention pressure are terminal batches collected and sorted by expiry, with oldest results removed until space is sufficient before checking active limits. Running and unknown work is not evicted. Terminal eviction updates this pass's counts without rescanning the table. Expiry removal schedules existing index/evidence cleanup without waiting for or claiming remote cleanup.

Before changing or removing an S3 connection, its encrypted record is durably saved to `.ycloud-system/retired-storage.enc` under the configuration directory. Only then is new configuration published. The file holds at most 64 records and 1 MiB, and credentials are not returned to clients. A separate task rotates through one record every 60 seconds with a 30-second cooperative cancellation budget, waiting for issued writes rather than dropping them. Network failure retains records for later attempts and restarts. Only provably owned transactions are recovered; buckets are not emptied and unowned orphans stay. In-process cleanup uses the original backend's gate, or the current gate when the same namespace is configured. A namespace cannot be independently re-added while its old cleanup is unfinished, avoiding confusion with new tasks. Completed cleanup removes the old credentials with the record. The original configuration master key must be retained.

S3 file and empty-directory deletion is successful only after the object is confirmed absent, not merely from DELETE status. Uploads verify the published object before returning success; temporary cleanup is not part of that success test. Foreground cleanup gets at most 500 ms, with the rest handled by durable recovery. Administrator cancellation before publication stops transfer without waiting for HEAD/Abort cleanup. Incomplete post-commit verification yields an unconfirmed result, not an ordinary failure or repeated write.

`s3_backend/deletion.rs` owns shared deletion and absence verification. Its general entry checks the current ETag. Directory-source deletion, directory-trash cleanup, and single-file move already verify size/ETag and reuse the verified execution boundary without a duplicate HEAD. Ordinary files, empty directories, and other cleanup retain the general entry. Conditional DELETE, OSS pre-delete checks, cancellable temporary cleanup, and non-discardable deletion of final objects keep their existing boundaries. One post-delete existence read settles responsibility only when absence is confirmed, even if DELETE returned an error. A present object or failed read preserves the original result and recovery responsibility. Single-file move still converts a delete substep's not-committed result into unknown for the whole move. Cleanup after verified directory completion remains committed/cleanup pending. This removes duplicate requests, not serial-deletion safety.

`read_journal_payload` in `s3_backend/journal.rs` bounds recovery-record reads. It validates declared length and requires ETag before collecting, then checks remaining capacity before appending each chunk. Small authenticated envelopes remain limited to 96 KiB and directory manifests to 4 MiB, with independent decoding, authentication, and structural checks. Chunked responses without declared length still respect the actual collection limit. Interrupted reads do not return partial records. Administrator read-pause control covers GET and body consumption; the request permit lasts through reading/validation. Errors refer to recovery records, without new codes or formats. These limits bound collected application bytes, not SDK chunks, allocation capacity, JSON-decoder memory, or process RSS. They do not apply to file payloads.

`s3_backend/transaction_record.rs` defines persistent upload/multipart models and namespace checks without remote calls. Other modules retain authenticated journal I/O, publication, and recovery. Uploads, moves, and directory operations keep their own commit proofs, record versions, and legacy compatibility.

`s3_backend/file_move_transaction/record.rs` defines the single-file move model and pure stage/identity rules. Its parent handles execution and authenticated journals. A copied-stage destination snapshot must match source size; this checks record consistency, not remote identity. Only preparation reads pre-copy metadata. Copied-stage recovery goes directly to source/destination size and ETag checks before deletion, without reading and discarding another snapshot. Source DELETE keeps the original ETag condition, followed by one existence check. Confirmed absence settles source deletion even after a DELETE error. A present source or failed check leaves the overall move unknown; a delete substep cannot overwrite the move's result. Version, JSON, and authentication are unchanged. Move is still not atomic.

`s3_backend/recovery.rs` centralizes order, classification, and dispatch for six journal categories. Startup recovery, online single-record recovery, and activation-probe cleanup share them. Business modules retain individual-record authentication, object checks, and recovery, not duplicate listing loops. Bounded listing checks exact prefixes, IDs, pagination progress, and limits. Before cleaning an internal upload intent, both recovery paths HEAD the same-ID upload transaction to prove absence; omission from a category listing is insufficient. Presence or read error stops work before reading/cleaning the intent payload. Online recovery still handles one registered journal per pass and releases gates afterward. Startup/post-interruption recovery processes all categories in order before read-only orphan counts for uploads/backups.

`s3_backend/multipart/session.rs` shares multipart preparation for uploads and server-side copies: persist a no-ID intent, create the remote session, then persist the provider ID. Only then does it return `StartedMultipart`, allowing part uploads, signing, or part copies. A creation result without an ID cleans only its intent; it neither guesses by object key nor enumerates remote sessions. Failed ID persistence attempts Abort with the known ID and keeps the record if that fails. `multipart.rs` coordinates uploads, `multipart/copy.rs` copies. Their completion proofs and errors remain distinct; direct/relay behavior, cancellation, and recovery are unchanged.

`s3_backend/directory_transaction.rs` coordinates preparation, per-object copying/deletion, and recovery. `snapshot.rs` owns bounded pre-write snapshots; `record.rs` handles manifest structure, authentication, and ownership; `journal.rs` handles remote manifests. Snapshot reads retain prefix checks, pagination progress, page/object/size limits, and administrator read-pause control, without publishing journals or changing final files. The directory manifest keeps its v2 JSON and authenticated bytes, not the upload envelope format. Limits remain 1000 objects, a 4 MiB manifest, and 5 GB per object. Recovery listing reuses safe pagination and common namespace/count/token rules. Implementation and tests stay separate.

Staging-object existence and size checks return the original metadata for later ETag validation. Probe errors, missing objects, and wrong lengths share not-committed cleanup. After failed publication, shared finalization is used only when the destination is confirmed absent or the old object has been restored with an updated rollback record. An unidentified final object keeps its transaction rather than being treated as safe to roll back.

Uploads, single-file moves, and directory changes share post-commit finalization. Once destination and source-deletion checks finish, an issued final-stage journal write must return. The 500 ms foreground window applies only to temporary garbage and transaction-record cleanup, not cancellation of a stage-journal PUT. Journal failure or slow cleanup does not reverse a verified committed result; authenticated records allow background verification to continue. Directory changes journal progress in batches, merging final progress into the final-stage record instead of reporting an already completed change as failed because of an extra write. Recovery still waits for confirmed cleanup before dropping responsibility. Failure after partial directory changes leaves the overall result unconfirmed; one undeleted object does not prove the directory was unchanged.

All three directory operations share one final-stage/cleanup exit. The record module maps each operation to its completion stage and validates stage/progress consistency. Copying cannot already have source deletions. The copy terminal stage is for copy only, with all destination identities recorded and sources untouched. Move/delete enter source deletion only after recording all destination identities; terminal deletion also requires every source confirmed gone. These checkpoints do not replace remote identity or absence checks. Inconsistent records stop and stay; progress is not guessed. Existing authenticated terminal stages do not rewrite the same stage or modify source/destination again. Cleanup still verifies trash identity per item and confirms journal deletion last. Failed initial terminal publication keeps the older journal for evidence-based recovery. Temporary-delete errors cannot replace a verified committed result; recovery cleanup errors report committed/cleanup pending with the original cause and prohibit repeating the file operation. Long directory operations still hold their existing gates and have no new cross-restart query receipt.

Zero-byte empty-directory markers use the same directory transaction for preparation, commit, and cleanup. Implicit empty directories without markers still reject the operation. The unused nontransactional `delete_empty_directory` entry is removed. Browser, batch, and WebDAV deletion still use the unified storage interface, with unchanged routes and recursive-delete rules.

Batch API `success` counts confirmed commits, including pending cleanup; `pending` counts unconfirmed results; `failed` counts definite failures only. Their sum is the total. Each item's `operation` retains commit/cleanup details. The frontend accepts older responses and distinguishes success, committed/cleanup pending, awaiting confirmation, and failure. Unknown items are not hidden or called successful just because `failed=0`.

`apps/browser/operationFeedback.ts` builds `BatchReport` in one pass over item results. Classification is separate from summary formatting. Notification color and detail rows use the same report rather than separate counters/template filtering. Pending cleanup is not a failure; unknown results use error feedback. Legacy-code compatibility and response order remain. A fully successful new response clears the previous report. This is a display model, not new backend evidence, retry policy, or persistence.

`apps/browser/useBrowserFileOperations.ts` holds one pending request for delete confirmation and move/copy selection, capturing operation, paths, and storage together. The page derives its dialog state from that request and clears it through one close path. The three writes share busy state. Move/copy close the selector before submission; definite delete rejection allows manual retry, while committed/unknown errors block repeating the current confirmation. Item results release busy state and display the report before independent directory refresh. Slow refresh does not block another confirmation or turn a read error into a write error, and cannot close a newer dialog. Unmount clears local confirmation/report state, not issued writes. Late results cannot notify, clear selection, or start reads. There is no automatic resend or cross-restart receipt.

Remaining limits: upload tickets have a persistent cross-restart result index, but some administrator operation receipts do not. Creation and password changes cannot be proven from lists alone. Disable, tighter policy, relay-mode change, and configuration removal can publish before whole-file operations finish; old executors retain settlement responsibility. Connection/mount changes still wait at most 5 seconds for storage exclusivity. Re-enable rejects old executors and pending recovery records. Disk publication and underlying I/O have no fixed elapsed-time guarantee. Single-file delete lacks a persistent cross-restart result receipt. Move/directory/batch regression coverage is not deployment validation for every operation and external modification.

## Browser tasks, login and permissions

`apps/browser/uploadQueue.ts` defines upload tasks and pure action-eligibility rules shared by buttons and queue handling, without Vue, API, or timer dependencies. Preparing, queued, and uploading tasks can pause; paused tasks can resume. Awaiting-confirmation tasks remain active but cannot be paused, stopped, or cleared again. Stop requests for mixed selections include only stoppable members, not successful, failed, or already stopped tasks. Stopping an active upload first interrupts transfer, then uses result verification. Clearing a selection requires every member to have ended. Unknown failures cannot be retried directly, but their browser records can be removed. Clear does not delete files; it releases only tickets no retained task needs, leaving server results and file evidence intact. Disposed-page controls do not change records, send requests, or show feedback.

The prepared browser queue runs at most four file executors. As one transfer ends, it takes the next file without waiting for the others. Each file has an independent cancellation handle; pause/stop affects only selected files, and unmount cancels all in-flight transfers. Verification after interruption does not occupy a file executor and does not retransmit unknown results. New unprepared tasks are prepared after the current wave. Four-file concurrency and four-part S3 concurrency per file are separate limits, still subject to account/storage admission and the global relay-payload budget.

The upload dialog derives normalized bytes, per-file progress, counts, and overall progress from one task model, not a second runtime state. Bytes from failed, stopped, or paused transfers are not completed work. Only all-confirmed-success displays 100%. Empty files/queues have separate handling; negative, oversized, or NaN progress cannot produce invalid percentages. The speed label is browser upload speed, not a claim that every S3 byte passes through Ycloud. Permissions, quotas, commit/cleanup rules, and part concurrency are unchanged.

`apps/browser/uploadTaskState.ts` interprets server status for display and retry eligibility only. It uses existing bilingual text selection and performs no requests, timers, notifications, or directory refresh. Confirmed completion takes precedence over local pause/stop intent; pending temporary cleanup is still success. Running/unknown results cannot be retransmitted. An administrator-closed task with unknown commit cannot be interpreted as definitely uncommitted. `useUploadQueue.ts` retains cancellation, feedback, and page lifecycle; success and exception paths share result verification for pause/stop. `uploadReconciliation.ts` manages bounded queries. Ticket checks, preparation, and transfer recheck disposal after waits. Late results cannot notify, refresh, prepare remaining batches, or start another file. Late preparation tickets use the existing cancel API; unmount during a prepared-item cancel also releases the whole ticket. Committed files are not cancelled. Sent status requests retain the shared deadline; ignoring a late result does not instantly end its underlying request.

`apps/browser/uploadTaskGroups.ts` groups by storage and ticket using only task-model types, not requests or status interpretation. Preparation, transfer, cancellation, release, and unmount share the rules. Ticket identity includes storage ID, preserving first-group and member order. Groups retain original task references so pause/stop changes during waits are not overwritten by copies; execution rechecks status and tickets. Batch status and server-numbered responses each build one path index for the current phase. Duplicate paths use the first match; missing numbered paths retain the original. Indexes are not cached across requests. Grouping, path matching, and release checks are linear traversals, without reading file bodies or changing concurrency.

`apps/browser/uploadReconciliation.ts` owns result reads, batch membership, and retry timers. Each storage/ticket has one verification chain with either one in-flight read or one timer; its pending files share a response-path index. A chain reads at most seven times: the first plus six delayed retries. Joining an active chain does not reset its budget. Resolved files leave; network failures and missing items get bounded verification, then remain unconfirmed without retransmission. Different storage/ticket pairs are isolated. Removed, resolved, or re-ticketed tasks reject old results. A computed Set invalidated by membership changes supplies retained task identity without rescanning the queue per file. Unmount clears timers/members and prevents late results from updating or rescheduling. Responses are not permanently cached; a later independent chain has its own budget.

Directory refresh after upload success does not block queue advancement. Ordinary success and verified success share one refresh entry. There is at most one in-flight refresh and one coalesced pending target, bound to storage/directory at request time. Execution and error feedback recheck the current page; navigation/unmount discard old targets and errors. Slow or failed reads neither block queued files nor reverse upload success. Read errors are separate and do not repeat uploads. `useBrowserListing.ts` still handles cancellation and stale results.

`apps/browser/uploadCandidates.ts` collects selected files/directories; `uploadQueue.ts` defines tasks; `useUploadQueue.ts` owns admission, tickets, transfer, and verification. Collection permits at most 20,000 entries before deduplication, counting dropped directories and files. The retained queue's 20,000-task limit is checked independently at admission, with unchanged server file/batch limits. An oversized selection or any read failure rejects the whole input, not a partial set. Directory traversal is iterative depth-first, reading chunks and awaiting one native callback at a time. Root, child, and chunk order stay intact; the entire tree is not expanded into concurrent Promises. The limit bounds application candidates, not a browser-created FileList, native callback chunk, or total memory. File bodies are not read. Drop captures storage and base directory before collection, so later navigation cannot redirect files to a new location. Leaving cancels collection waits; late callbacks/errors create no tasks or feedback. Already issued native callbacks cannot be cancelled. Existing tickets, commit/cleanup behavior, file execution order, and part concurrency are unchanged.

`apps/browser/useBrowserListing.ts` handles listing cancellation, request order, and page state. `storageSelection.ts` handles selectable storage, preference invalidation, and identity-scoped preferences. Temporary health failures do not clear preferences; disable, revoked permission, and removal do. Unavailable browser storage does not block listing. Results share one application path; old entries/permissions share one reset. Only the current request applies results or writes preferences. API capabilities take precedence over legacy `can_write`. Storage changes and re-login clear old entries/permissions before awaiting new results.

`apps/browser/useBrowserDownloads.ts` handles download checks and archive preparation independently of write dialogs, selection state, and directory refresh. `useBrowserFileOperations.ts` handles batch changes; creation/rename have their own editor. Single-file checks deduplicate by full URL. Archive preparation shares a busy state without blocking single-file checks. Requests capture storage and paths; archive-limit feedback uses the captured limits, not a later storage selection. Unmount ignores late results and prohibits feedback/navigation, without cancelling accepted archive preparation. Requests retain the common deadline and are not repeated automatically. Permissions, archive limits, tickets, and streaming archive rules stay unchanged.

`apps/browser/useBrowserEntryEditor.ts` manages folder creation/rename drafts, captured request context, and lifecycle through one short-field dialog. Named operations distinguish create from rename without a generic CRUD framework. Opening checks the corresponding capability; the server still validates permissions and names. During a write, the editor cannot close or be replaced; backdrop and cancel share this rule. Committed/unknown errors use `ApiError.blocksRetry` to block another confirmation. Definite rejection keeps the draft for correction and manual retry. Confirmed success closes the editor, releases busy state, and notifies before independent refresh. Read failure does not enter the editor's write error or repeat the operation. Unmount clears local state and ignores late writes, but does not cancel issued requests or start a departed page's refresh. No cross-restart receipt is added.

`apps/browser/useBrowserPreviews.ts` owns image navigation, audio queues, file-dialog targets, and fallback-download confirmation. The page retains player expansion, display, and download execution. File dialogs, fallback downloads, and audio queues bind to entry snapshots and storage at opening. Same-storage refresh does not replace a playing queue; storage changes clear preview interaction synchronously. Dialogs use a storage/path component key to avoid old reads when a file changes. Audio-error checks use the existing bounded HEAD interface; open, close, change, and unmount invalidate old results so an empty player cannot reopen an old confirmation. There is no polling or automatic download. List/gallery clicks share `openEntry`; thumbnails/navigation share `previewKind`. Closing previews does not cancel unrelated writes. This module does not read document bodies, own media controls, or validate server permissions.

`shared/api/textPreview.ts` and `shared/composables/useTextPreview.ts` share text reads between dialogs and standalone previews. The API handles Range, bounded body collection, and HTTP errors; the composable owns target state and request lifetime. The common timeout covers body consumption. Target changes, preview disable, and unmount cancel old reads and ignore late success/failure. Requests ask for the first 2 MiB and retain at most 2 MiB even if storage ignores Range. Content-Range or an extra body read establishes truncation before further consumption stops. This is not a hard browser-memory or network-byte limit. Complete HTML keeps sandbox/CSP; truncated HTML displays source only. Download errors do not replace text-read results. There is no automatic retry or new query framework.

`shared/composables/useMediaPreview.ts` handles PDF/media quota diagnostics for dialogs, standalone pages, and galleries. `usePreviewDownload.ts` handles download admission, duplicate-click protection, and feedback for those views. Each binds to the complete file/storage URL. Target change, disable, and unmount cancel old HEAD reads and check cancellation before feedback/navigation, including a round trip to the same target. Ordinary media gets one diagnostic after load failure. PDF checks quota before display and can diagnose a later load failure once. There is no continuous probing or automatic retry. HEAD keeps the common deadline and existing boolean diagnostic result. An inconclusive network error is neither quota exhaustion nor proof of preview availability; GET and backend permissions decide the read. A changed target cannot start an old download. Failed downloads allow manual retry; an already-started browser download is not cancelled. Listing downloads/archives stay with `useBrowserDownloads.ts`, and preview close does not cancel background writes. Gallery zoom/pan resets by full source URL, not path alone.

`shared/composables/useMediaPlayback.ts` owns DOM playback state, progress/volume/loop synchronization, and resource lifetime. `MediaPlayer.vue` keeps layout, volume popup, fullscreen, and previous/next navigation. Audio and video share events and bounded progress rules. Source changes replace the media element. Old elements remove listeners, pause, remove src, and call load on replacement/unmount, without guaranteeing immediate memory release. Each element has at most one pending play request; late rejection affects only a still-current target. AbortError from pause/load is not reported as file corruption. Each new element attempts autoplay once; a browser-policy rejection leaves manual playback available. Volume popup IDs are unique within the app; source/type changes close the popup, and Escape returns focus. Appearance, permissions, and accounting are unchanged.

Administrator password/TOTP changes revoke only administrator sessions. Ordinary-user quota changes do not log users out. Actual changes to password, username, enabled state, or storage permissions revoke that user's sessions. Server file authorization remains mandatory even if a browser displays an old page.

`webdav/access.rs` owns mount authentication, durable failure limiting, and read-only authorization; `webdav.rs` keeps protocol dispatch and storage operations. Mounts require independent Basic credentials, not passwordless public access. An initial challenge without credentials does not count as failure; incorrect supplied credentials do. A read-only mount can authenticate successfully while rejecting writes, without counting that as a password failure. Password execution waits at most 3 seconds for admission; started computations keep their permits until finished. DAV retains a separate request-admission gate.

`webdav/credential_cache.rs` stores only proofs of successful Argon2 checks. It holds at most 64 entries, each expiring after 5 minutes without extension on hits; capacity eviction removes the earliest insertion, and restart clears it. A proof is HMAC-SHA256 under a process-local random key, bound to the complete current mount configuration and supplied password. It stores no plaintext password, request headers, or configuration snapshot. Every request still reads current mount settings, checks enabled state, IP bans, and read-only permission, and follows existing login logging. Bad credentials are not cached. Changes to credentials, mount path, storage, or permissions invalidate matching. Locks do not span password, file, or ledger I/O. The design references [SFTPGo's WebDAV authentication cache](https://github.com/sftpgo/docs/blob/main/docs/config-file.md#cache), without its indefinite-cache setting. Run `cargo test cached_webdav_authentication_baseline --locked -- --ignored --nocapture` to compare cold and warm authentication locally, not to measure remote throughput or phone compatibility.

WebDAV PUT shares the single-file upload limit, initially 5 GiB subject to deployment limits, capacity reservations, site-wide traffic quota, and global upload rate. Local PUT accepts known or unknown body length; S3 PUT requires valid Content-Length. Downloads have no separate file-size limit but retain site-wide quota, global rate, and backend stream permits. Single Range is supported; HEAD neither transfers nor counts body bytes. Rate 0 means no application-level limiting. Each direction shares its rate across related transfers, not per task. DAV admits at most 8 handlers; PUT holds admission until completion, while GET releases DAV admission after returning headers and keeps the backend stream permit for the body. Local writes share 4 I/O permits by default, and each local instance defaults to 4 download-stream permits; these are not four tasks per phone. Request handling defaults to 300 seconds and PUT to 6 hours. GET's server handling timeout ends when the response is established, not after its complete body. Clients/proxies have separate timeouts. A client Read timed out cannot prove the file was not committed. Browser four-file scheduling, automatic numbering, and direct S3 upload do not apply to DAV. PUT retains replacement semantics without resumable writes or automatic retry.

GET and HEAD share backend response policy and range reads. HEAD keeps file headers, removes the body, and skips download accounting/rate wrappers. PUT, DELETE, MKCOL, MOVE, and COPY share `mutation_response`: committed/unknown backend errors retain commit, cleanup, and retry details rather than collapsing into one status. Ordinary protocol errors retain their status. Destination parsing occurs only for MOVE/COPY and remains restricted to the same host and mount.

## Status, memory and traffic

A green storage indicator means the last connection operation succeeded; red means a failed check or an unprepared backend. Reads, transfers, and mutations may update this cache. Invalid paths, quotas, and permission errors do not imply a broken connection. A health task separate from cleanup checks cached instances every 300 seconds with a 10-second check budget. The visible admin storage page reads status every 300 seconds; display APIs do not probe repeatedly. This is not disk-health monitoring or a live SLA. Disabled state is separate, and instances that failed startup preparation need re-enable/edit initialization.

The admin overview reads domain, limits, accounts, and storage configuration under one configuration lock, then releases it before reading runtime storage/mount state. Configuration fields share a snapshot; health and usage are later runtime observations, not an atomic cross-storage instant.

New S3 storage defaults to browser-direct uploads, at most four concurrent parts, with a base size of 64 MiB. Large files increase part size to stay within the part-count limit. Payload bypasses the VPS. Live speed is browser sending speed, not proof of storage commit. Each account may have at most four unfinished batches and four executing direct-file tasks, shared across login sessions. Excess admission is rejected rather than queued indefinitely.

Relay forwards while receiving without caching complete parts. Small files and WebDAV uploads share the process-wide payload-byte budget: 1/32 of detected memory limit, clamped to 4–32 MiB; failed detection defaults to 16 MiB. A 1 MiB window is reserved before reading the request body. A full budget pauses intake; the final data reference returns the reservation, including on failure/cancellation. Direct uploads do not use it. TLS, SDKs, and other work still consume memory, so this is not a hard RSS ceiling.

Ycloud counts and limits file bytes passing through the VPS, not total physical-interface traffic. Direct uploads/downloads are excluded from administrator, user, guest, and site-wide usage. Quota-only edits retain existing reset timestamps and timezone.

Browser downloads and previews share storage authorization, folder locks, backend reads, and VPS accounting/rate limits. They differ only in attachment versus safe-preview response policy. Previews cannot bypass download permission or traffic controls.

`storage/read_conditions.rs` owns range and version decisions. Local reads open the file under a stream permit and use the same handle for metadata and body, avoiding a length from one file and bytes from its replacement. External in-place edits are not snapshot-isolated. S3 metadata supplies ETag, and body GET uses that ETag as If-Match. HEAD ignores Range, returning complete metadata and no body; S3 does not issue an extra body GET. Local HEAD releases its handle/permit on return while retaining permission checks and browser quota diagnostics.

`If-Range` accepts only one strong ETag matching the current object. Mismatch, weak tags, absent tags, or date conditions return full 200 rather than splicing versions. Dates cannot prove strong consistency here. Local files expose Last-Modified, not a size/time-derived strong ETag or a per-download whole-file hash. Ordinary single Range returns 206; invalid ranges return 416. This read path does not own write conditions or ledger formats. Its regression tests do not establish that phone-upload timeouts are solved.

`webdav_xml/query.rs` parses XML selectors, `webdav_xml.rs` emits responses, and `webdav/error.rs` converts protocol errors. PROPFIND interprets prop/propname/allprop/include by namespace. Empty body means allprop; duplicate properties deduplicate by namespace/name. Unknown properties get separate 404 propstat entries, not successful values. propname returns names only. The existing five properties remain; getetag, creation time, and lock support are not fabricated, and no extra object metadata probes are added. Collection hrefs end with a slash. DTD entities are not expanded, with no external-entity resolver. roxmltree uses only std rather than a custom XML parser.

PROPFIND control bodies are at most 64 KiB, parsed into at most 2048 nodes and 128 requested properties before deduplication. Namespaces are at most 1024 bytes and local names 256 bytes. Generated bodies are at most 8 MiB; excess returns 503 asking for a narrower query, not truncated 207. This is not an RSS bound, and directory-entry limits apply separately. Depth accepts only 0, 1, or infinity; invalid/duplicate values return 400. Directory infinity or an omitted header returns 403 with DAV:propfind-finite-depth, not silent one-level fallback. File infinity does not recurse directories. See [RFC 4918 §9.1](https://www.rfc-editor.org/rfc/rfc4918.html#section-9.1).

Absolute MOVE/COPY Destination compares parsed authority, including host and effective port. Host case and omitted default HTTP 80/HTTPS 443 are equivalent; different hosts/ports and query strings are rejected. The destination stays within the mount. Relative destinations retain path rules, and percent decoding happens once. This comparison neither infers TLS nor establishes proxy trust. Ordinary backend errors use AppError's safe body and existing capability codes, without exposing internal context/sources. Committed/unknown evidence and no-repeat rules remain. A 401 includes a Basic challenge. Unconditional upload keeps replacement/commit rules; conditional writes use the limits below.

The dashboard labels are “Total download” and “Total upload,” with a short note that only Ycloud file transfers count and direct S3 traffic is excluded. This wording does not expand accounting.

On desktop, the traffic trend grows with the shared two-column row, aligning its horizontal-axis bottom with the ring-chart legend rather than leaving space below a fixed-height chart. Ring tooltips overlay content instead of reserving a blank row. Narrow screens keep stacked charts and a 220 px minimum trend height. Small nonzero bars and hover rules remain visible. Only layout changes; traffic values, proportions, and dates are unchanged.

`apps/admin/useTrafficSettings.ts` owns quota editing; `TrafficPanel.vue` keeps charts/date queries. The editable snapshot copies only site-wide, guest, aggregate-user quotas, and reset cycle, not independent account quotas. Save compares named fields and sends changed groups only, independent of JSON order. Untouched cycle controls preserve timestamp/timezone. Drafts and submitted values are independent of refreshing statistics, and busy saves do not duplicate requests. Feedback, statistics refresh, and readback after lost responses use existing paths without changing accounting.

Uploads and downloads share bounded frame batching. It combines only ready frames and stops after reaching 256 KiB or inspecting 64 frames, without waiting to fill the batch, starting prefetch work, or buffering a whole file. An upstream frame may exceed the byte target; it is charged whole, without an uncharged tail. The target is not a hard upstream-frame or RSS bound. Each batch checks quotas and durably charges before releasing the original byte segments downstream. Cancelling an HTTP waiter does not cancel an issued ledger write. Format, corruption rejection, and restart replay are unchanged. These are bytes admitted through that boundary, not bytes acknowledged by the peer; downstream interruption does not retract a released batch. `cargo test batched_frame_accounting_baseline --locked -- --ignored --nocapture` compares local per-frame and grouped synchronization, not deployed throughput or CPU.

Local downloads read in 256 KiB windows, constrained by Range and existing stream permits. Local uploads coalesce small writes into a buffer of at most 256 KiB, not a whole-file cache. Buffered or not-yet-written bytes keep physical-space reservations; completed writes release them. The tail is written before publication. Final file sync, atomic commit, and the operation receipt remain the success boundary. Interrupted uncommitted uploads clean only their staging file, never final files. Completion stages over one second log buffered-write, file-sync, commit-gate wait, publication, and capacity-settlement times. Ticket-result persistence over one second is logged separately to explain server waits after 99%; browser sending completion is not upload success.

`traffic/commit.rs` has one executor owning ledger files. Its pending channel holds at most 64 requests. It combines at most 64 already-arrived records into one append/sync, without a timer to fill batches. Cumulative quotas are checked in order against a candidate ledger. Only disk success publishes the confirmed ledger and releases streams; rejected requests add no record. The public ledger lock does not span disk I/O, so statistics/configuration reads do not wait for synchronization. An enqueued request is settled even after its HTTP waiter disappears; admission backpressure can be cancelled before enqueue. Disk failure stops further metered release and preserves the original ledger for recovery rather than zeroing it. Sequence, replay, and compaction rules remain. WebDAV and browser traffic share this path; accounting is not deferred until upload success or a lossy periodic flush.

In-flight upload/download streams keep the `transfer_limit.rs` adapter even at rate 0. Switching to a finite rate affects future unconsumed frames; switching back to 0 wakes waiters. Every rate change notifies waiters to recheck the shared token bucket. No lock is held during sleep and no uncancellable token debt is reserved. The zero-rate path checks the current rate without taking the bucket lock. Released frames cannot be recalled. Streams share one bucket per direction, separately from quotas. Configuration cannot retrieve bytes already written to the network or guarantee strict fairness.

S3 upload/multipart and directory journals share `s3_backend/journal.rs::write_encoded_journal`. It accepts encoded bytes and handles provider condition headers, admission permits, recovery registration, remote PUT, and response ETag checks. Callers retain authentication, schema checks, and manifest limits; existing record formats stay. Standard S3 creation uses If-None-Match and updates use If-Match. OSS retains its no-overwrite header and pre-update version check. That compatibility branch is not atomic CAS against external writers and does not expand the single-writer guarantee.

Production browser uploads use operation-bound receipts. `StorageBackend::upload_new_file` without an operation ID and `S3Backend::copy_directory` without expected size compile only as test fixtures, not runtime alternatives. Existing browser storage prepare/activate/discard APIs and migrations remain. Direct-upload progress adds deltas from each part's cumulative count so duplicate final progress events do not double-count. Four-part concurrency, cancellation settlement, and commit verification remain.

Large directory snapshots sort on a blocking thread within their existing build permits, not on an async request thread. The two-build budget per instance, cache invalidation, and pagination remain. Conflicting directory mutations are not parallelized.

Historical Windows debug baseline, 2026-09-27: 1024 durable 64 KiB charges took about 632 ms, or about 101 MiB/s for accounting alone. This predates bounded grouped commits and does not measure current end-to-end transfer or NAS/VPS disk performance. Passing unit tests does not prove deployed 99% waits or CPU usage are solved. New-image measurements still need to distinguish proxy transfer, Ycloud completion logs, and disk synchronization.

## Conditional WebDAV writes

`storage/write_conditions.rs` parses and evaluates conditions, without a second page/handler implementation. PUT accepts If-Match/If-None-Match and If-Unmodified-Since. Tag lists are limited to 4096 bytes and 32 entries; commas inside quotes are not separators. If-Match uses strong comparison and If-None-Match weak comparison. If-Match takes precedence over dates. Invalid dates are ignored under HTTP rules, while duplicate dates are rejected. See [RFC 9110 §13.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.2). This is limited conditional support, not full WebDAV conditions/locking.

| Case | Behavior |
| --- | --- |
| Local PUT with If-Match: * / If-None-Match: * | Check existence/absence before receiving and again under mutation_gate before atomic commit. Failure returns 412. |
| Local PUT with modification-time condition | Compare actual modification time at second precision, only without If-Match. This cannot detect every same-second change or prevent external writes that bypass Ycloud. |
| Local PUT with explicit tags | Local storage emits no strong ETag. Explicit If-Match cannot match and returns 412. An unverifiable explicit If-None-Match on an existing file returns a capability error rather than guessing and overwriting. |
| Conditional S3 PUT, excluding OSS | Limited to single-object atomic copy, at most 4 GiB. It needs returned ETags and verified condition support. A fresh destination read binds the decision version to the publishing CopyObject request with If-Match or If-None-Match. |
| Standalone S3 date conditions, conditional OSS PUT, or conditional PUT above that size | Reject before the publication request. A date already superseded by If-Match is not evaluated separately. Ordinary unconditional uploads remain available. |
| Effective conditions on DELETE/MKCOL/MOVE/COPY and other writes, or DAV If lock conditions | Return 501 rather than ignoring the condition and changing files. Unconditional methods retain existing behavior. |

Local checks run in `ReplacementObserver::check_destination`, before transaction ownership transfer, journaling, and rename. Failure cleans only this staging file, without changing the destination or committing logical capacity. Receipts, atomic replacement, and space reservations remain, without whole-file hashing or a local version database. Definite precondition failure uses `precondition_failed`/HTTP 412; internal errors use the shared error protocol.

`conditional_publish.rs` coordinates S3 publication. First use places an empty object at the registered upload transaction's private backup key to verify rejection of mismatched versions and no-overwrite requests on existing objects. It does not copy file payload, change bucket rules, or modify final files. Success is cached only in the current client instance, rechecked after restart/connection change and reused on metadata edits. Conditional uploads do not back up the old final object or restore a backup on failure. Publication copy is sent once with SDK retries disabled, avoiding a successful first request followed by retry 412 being misreported as uncommitted.

Authenticated conditional-upload journals use v2, binding conditions and CheckingPublication / PublicationStarted / PublicationRejected stages. Checking proves publication has not started. Explicit rejection proves this publication request did not commit; recovery cleans only private objects with the same ID, correct operation marker, and size. Started publication confirms success only through the current final object's operation marker and size. It cannot infer failure from a staging ETag, an old file still present, or a missing destination. Inconclusive evidence retains journals/resources and never restores the old file or resends publication copy. A crash between journal publication and sending the request can remain unknown, so not every unknown result is guaranteed to settle automatically. Rejection journaling returns before the shared 500 ms cleanup window. Unfinished cleanup retains responsibility; the window does not interrupt an issued stage-journal write.

Unconditional uploads keep v1 journals without new fields. Existing v1 records remain readable, and Multipart v1/v2 formats are unchanged. Do not downgrade to an old binary while v2 conditional transactions remain; it cannot read the new stages/fields. This adds no unified cross-restart WebDAV receipt and does not extend upload-ticket queries. Real S3, Linux power-loss, and weak-network phone testing remain outstanding. Protocol regressions do not identify the cause of a phone's 400 response or upload timeout.
